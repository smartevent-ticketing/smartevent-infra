Mục tiêu và phạm viSmart Event Ticketing Platform là nền tảng cho phép organizer tạo sự kiện, thiết kế khu vực/ghế, mở bán nhiều đợt vé, xử lý giữ vé - thanh toán - phát hành ticket QR, đồng thời hỗ trợ vận hành sau bán như check-in, refund, resale, recommendation và analytics.Nhóm người dùngMục tiêu nghiệp vụChức năng chínhCustomerTìm và mua vé an toàn, không bị bán trùng.Đăng ký/đăng nhập, tìm event, chọn khu vực/ghế, giữ vé, thanh toán, nhận QR, favorite, review, resale.OrganizerTạo và vận hành event.Tạo venue/event/area/seat map, ticket types, sale phases, coupon, staff, check doanh thu, analytics.AdminKiểm soát chất lượng và rủi ro nền tảng.Duyệt event, quản lý user/review/refund, giám sát payment, audit, cấu hình hệ thống.SystemTự động hóa các workflow nền.Mở/đóng sale phase, expire reservation, release inventory, xử lý webhook, phát hành ticket, gửi notification.1.1 Phạm vi đầy đủCore ticketing: event, venue, area, seat, ticket type, sale phase, reservation, order, payment, ticket QR, check-in.Growth/operation: categories, search/filter, coupon, favorite, review, notification, event staff và quyền theo từng event.Production-grade concerns: concurrency, locking, idempotency, audit log, monitoring, storage lifecycle, CI/CD, deployment.Advanced scope: refund, resale marketplace, recommendation system và analytics/warehouse.1.2 Ngoài phạm vi phiên bản thiết kế nàyKhông viết code implementation, SQL migration chi tiết hoặc UI mockup.Không chốt nhà cung cấp thanh toán cụ thể; thiết kế cho phép tích hợp VNPAY, MoMo, Stripe hoặc provider tương đương.Không bắt buộc microservice ngay từ đầu; ưu tiên modular monolith để giảm độ phức tạp triển khai.2. Concurrency, locking và chống oversellNguyên tắc: Redis giúp nhanh và giảm tải, nhưng PostgreSQL transaction mới là chốt chặn cuối cùng. Không được dựa vào cache để đảm bảo không bán trùng.7.1 SEATED inventoryKhi user chọn nhiều ghế, backend luôn sort event_seat_id tăng dần trước khi lock để giảm deadlock.Backend mở transaction và lock row event_seats theo thứ tự đã sort.Chỉ update thành HELD nếu status hiện tại là AVAILABLE hoặc HELD đã hết hold_expires_at.Tạo reservation_items gắn event_seat_id và expires_at.Khi payment success, lock reservation + seats rồi chuyển HELD -> SOLD.Khi reservation expired, worker chuyển HELD -> AVAILABLE nếu chưa CONFIRMED.7.2 STANDING inventoryMỗi sale phase có đúng một inventory_counters row là nguồn thật cho total_quantity, held_quantity và sold_quantity.Không dùng sold_count/held_count trong ticket_sale_phases cho booking path; nếu cần hiển thị nhanh thì chỉ dùng read-only denormalized cache được rebuild từ inventory_counters.Hold quantity bằng atomic conditional update: held_quantity = held_quantity + requested WHERE total_quantity - held_quantity - sold_quantity >= requested.Nếu UPDATE affected rows = 0 thì trả SOLD_OUT hoặc NOT_ENOUGH_INVENTORY.Payment success chuyển held_quantity giảm và sold_quantity tăng trong cùng transaction.Expiry worker giảm held_quantity cho reservation hết hạn.7.3 Locking strategy đã chốtChốt quyết định: Booking path dùng pessimistic row lock/atomic conditional UPDATE trong PostgreSQL. Không dùng optimistic version cho inventory hold/sell, vì vé là tài nguyên tranh chấp cao và cần fail nhanh, rõ ràng.7.4 Max per user concurrencyTrước khi hold, backend UPSERT row user_sale_phase_counters(user_id, sale_phase_id) nếu chưa tồn tại.Trong cùng transaction hold inventory/seat, backend chạy atomic conditional UPDATE trên user_sale_phase_counters: held_quantity = held_quantity + requested WHERE held_quantity + purchased_quantity - refunded_quantity + requested <= max_per_user.Nếu UPDATE affected rows = 0 thì trả MAX_PER_USER_EXCEEDED và rollback toàn bộ hold.Payment success chuyển held_quantity giảm và purchased_quantity tăng trong cùng transaction confirm reservation.Reservation expiry giảm held_quantity tương ứng.Refund completed tăng refunded_quantity hoặc giảm purchased_quantity theo policy báo cáo, nhưng phải giữ lịch sử qua refund_request_items.7.5 Redis phối hợp thế nàoRedis key seat_hold:{eventId}:{seatId} TTL 5 phút giúp UI biết ghế đang bị giữ gần realtime.Redis distributed lock chỉ dùng rất ngắn để giảm tranh chấp, không thay thế row lock.Redis cache inventory có thể stale vài giây; checkout luôn verify lại với PostgreSQL.Reservation expiry dùng cả Redis keyspace notification hoặc delayed queue, nhưng worker vẫn query PostgreSQL để tránh mất event khi Redis restart.Rủi roCách xử lýHai user cùng giữ một ghếRow lock hoặc conditional update trong PostgreSQL; chỉ một transaction update được AVAILABLE -> HELD.Deadlock khi giữ nhiều ghếLuôn sort event_seat_id tăng dần và lock theo cùng thứ tự trong mọi transaction.Oversell standing ticketAtomic update inventory counter với điều kiện available >= requested.Worker expiry chạy trễReservation có expires_at; payment success phải reject nếu reservation đã hết hạn.Redis mất dữ liệuPostgreSQL vẫn có reservation và hold_expires_at; cache được rebuild.7.6 Virtual Queue / Admission ControlVới event hot, row lock vẫn bảo vệ đúng dữ liệu nhưng không bảo vệ trải nghiệm người dùng khỏi thundering herd. Virtual queue là lớp admission control trước reservation endpoint, dùng Redis để chỉ cho một lượng user vừa phải đi vào booking path trong mỗi batch.User request  -> Rate limit by IP + user_id  -> If virtual_queue_enabled:       LPUSH/ZADD into vq:{eventId}:{phaseId}       Return position + estimated wait time       Worker admits batch N users every 3-5 seconds       Issue booking_token TTL 2 minutes       Reservation endpoint verifies booking_token  -> Else:       Process reservation normally with PostgreSQL locksThành phầnThiết kếQueue keyvq:{eventId}:{phaseId} dùng Redis List hoặc Stream; phần tử chứa user_id và timestamp.Position trackingvq:pos:{eventId}:{phaseId} dùng Redis ZSET, score là join timestamp, ZRANK để trả vị trí.Booking tokenvq:token:{eventId}:{userId} là UUID TTL 2 phút; reservation request phải gửi token này.Batch admitWorker mỗi 3-5 giây cấp token cho N user, N dựa trên capacity xử lý hiện tại.Scope đồ ánKhông bắt buộc làm full waiting room; tối thiểu nên làm Redis rate limiting cho reservation endpoint và mô tả virtual queue khi vấn đáp.8.
